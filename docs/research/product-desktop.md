# LearnHarness product, interface, desktop, and integration audit

Audit date: 2026-10-29. Source baseline: **LearnHarness 0.4.0**, commit `dc4c398d5167865b84b0ccb3ec809eb88bf8f65f` on upstream `main`. The user's installed app is **0.3.8**, independently inspected by the primary investigator. **This report describes source-derived capabilities of 0.4.0, not a claim that each exists or was exercised in 0.3.8.** See the runtime investigation for shipped-artifact evidence and version differences.

Evidence boundary: normal read-only repository analysis across `app/`, `components/`, `electron/`, relevant `src/core`, `src/server`, integration adapters, configuration, and named tests. No app model call, subscription sign-in, destructive action, or test suite was executed for this report. `U` IDs identify product parity requirements; learning internals are cataloged separately in `learning-engine.md`. Inline links are pinned to the audited commit, so later upstream changes do not move the evidence. [Machine-readable route/dependency inventory](product-source-inventory.json) accompanies this report.

The product is a desktop/local web learning workspace with two central surfaces: a knowledge map and a session. Its character comes from structured questions, recording learner reasoning, visible plans, practical problems, and background agents. The surrounding shell is comparatively quiet. The actual implementation includes more controls than the README names, but several dependencies and old architecture descriptions should not be mistaken for currently reachable features.

## 10. Recommended improvements, explicitly new design choices

These are suggestions for CoquiLearn, not features attributed to LearnHarness:

1. Preserve deep learning interactions but reorganize settings around connection health, learning behavior and appearance, with progressive disclosure for low-level graph physics and token budgets.
2. Implement real light/dark/system modes and iOS-style glass for navigation/controls while keeping reading and answer surfaces calm/opaque enough for contrast; support Reduce Transparency and Reduce Motion everywhere, including canvas and scripted scrolling.
3. Retain Cmd/Ctrl shortcuts but restore conventional accessible Tab navigation/focus rings in menus and forms; custom choice row keyboard behavior can coexist with standard semantics. The map needs an accessible list/tree alternative rather than relying solely on pixels.
4. Store API/subscription secrets using OS credential storage where viable; keep provider routes explicit, with no stealth API fallback. Add per-session budgets and a preflight estimate before expensive background work.
5. Make source provenance inspectable at proposition and reasoning-step level; show contradictory/uncertain evidence without labeling learner ability as a single static score.
6. Add learner-goal dashboard, progress timeline, spaced retrieval/review queue, saved notes/bookmarks and useful export/import/migration workflows, each grounded in durable session evidence.
7. Improve artifact workflow: browse generated visuals/demos separately, reopen/download original assets, version repaired demos, and offer clear permission/capability boundaries for external resources.
8. Add bundled offline/local-model connection presets where technically supportable; current generic custom endpoint is a useful mechanism but not a full offline learning guarantee.
9. Provide backup/restore, schema migrations, transactional data and recoverable deletes. LearnHarness plain-file evidence is transparent; CoquiLearn can retain inspectable exports while gaining robust internal persistence.
10. Desktop remains the best first implementation target for local-file/CLI parity. An iPhone/iPad companion should use explicit synced learning/session APIs and a mobile-native glass UI; Electron/desktop CLI features cannot simply be shipped on iOS unchanged.

## 11. Coverage and residual unknowns
